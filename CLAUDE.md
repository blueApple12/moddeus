# Moddeus

Fabric mod for Minecraft **26.3** (Java 25, unobfuscated, Mojang names) that puts Claude Code inside a live singleplayer world. Plan: PLAN.md.

## Live workflow (game is usually running)
- Game runs from this project: `play.bat` → `gradlew runClient` on JetBrains Runtime 25 (`.tools/jbr`) with `-XX:+AllowEnhancedClassRedefinition` + our agent (`src/agent`).
- After editing code: **nothing to run**. The game auto-builds on save: `client/game/SourceBuild` = in-game incremental javac (changed files only; dependents only when a class API changed) + resource copy to build/resources, swapped by `HotReloader` **in the running world**, ~0.1 s save→live (OS file-watch event + 15 ms quiet, javac ~40 ms, core redefine ~60 ms; mod classes use generations instead). Gotcha: `JavacTaskPool` (JShell's reusable javac context) is NOT usable here: recompiling a same-named class makes later compiles fail with "cannot find symbol". `mc build` = same + prints compile errors (auto-build only logs them: "Auto-build:" in latest.log). Game closed: `mc build` falls back to Gradle. New classes and mod-project classes (Gens) take any change live; existing core classes take body-only changes live, and field/method changes wait for a restart (see Lag section).
- Code that must re-run after a swap (registrations, listeners) goes in a `static void` method annotated `@OnReload` (`dev.moddeus.live.OnReload`).
- Changes under `assets/` trigger a client resource reload (the F3+T loading screen). Changes under `data/` trigger a datapack reload. Never require leaving/rejoining the world.
- Results show up in `run/logs/latest.log` (search "Hotswap") and in game chat.
- **New content mid-game**: register through `LiveRegistry.register(BuiltInRegistries.X, id, key -> ...)` inside an `@OnReload` method, and also call it from `onInitialize` so it exists on the next launch. It thaws the frozen registry and binds tags, block-state ids and item components. Example: `content/ModBlocks.java` (Rizzium).
- New classes containing `@OnReload` methods are loaded and their hooks run automatically. Hooks run on the server thread while the client thread waits.

## Fast path (use first)
Blocks, items, food, textures and sounds (including from web URLs) take **one command, ~3-5s, live**: `node tools/mc.mjs ...`. See skill `mc-content`. Data lives in `src/main/resources/moddeus/content/*.json` and is loaded by `ContentLoader`.
- **Plumbing only.** One-command tools register and wire things (blocks/items/mobs, namespaces, tabs, pixel textures, sound import, recipes, cube models). Abilities, VFX, boss attacks, mob AI, sound design and model looks are written per mod in Java (`content/<Id>*.java`) so mods don't all look the same. Presets (`--preset`, `vfx-tex --shape`, `--model <shape>`, mob model presets, `synth --preset`, Bosses/Combat sample names) print "preset = sample only" and are reference code to read; the guides teach the how (toolbox "WRITE IT YOURSELF").
- **No Moddeus slash commands** (player's call): engines are Java APIs (`Vfx.play`, `Bosses.attack/behave/variant/arena/chest`, `Combat.exec`, `SoundLoops.follow/at/stop`, `Systems.coins/addCoins/openShop/startSky`, `WorldFeel.toast`, `Physics.spawn`), imported in `mc game run` snippets. Boss JSON: vanilla lines in `"cmd"`, engine attacks in `"attack"` / `"death_attack"` (`live/Api.attacks`). A mod gets a slash command (`mc command`) only when the player asks for one. `live/Api` also strips the old literals from a running server.

## Self-improvement (you may change ANY of this, including the reloader itself)
- In-game chats learn from feedback (toolbox "LEARN FROM EVERY MESSAGE"): generic bugs get fixed in core, taste rules go in with `mc lesson "<rule>"` (toolbox.md LESSONS, injected on every prompt; `mc lessons` lists them), how-tos into the guides.
- Everything here is fair game, including `HotReloader`, `LiveRegistry`, `ContentLoader`, `tools/mc.mjs`, this file and the skills. The reloader hot-swaps itself.
- When a task is repetitive or slow, turn it into a `tools/mc.mjs` subcommand or a skill. When you hit a gotcha, add it below.
- When editing `HotReloader`: `apply()` may be the OLD code when it swaps itself. Anything after `redefineClasses` must go through `afterSwap(Object[])`, whose signature stays fixed. Never add lambdas after the swap point. Breaking this crashed the game once (NoSuchMethodError lambda$apply$N).
- This shell sets `NoDefaultCurrentDirectoryInExePath`, so call scripts/bat files by absolute path (`& "<proj>/gradlew.bat"`).
- In-game chats must start the game DETACHED (`cmd /c start "" "<proj>/play.bat"`), never as their own child: a game started from a chat lives in the bridge's PTY and dies when the bridge restarts (lost the world session once).
- If the game is not running: `play.bat` starts it and auto-joins the last world. Use the absolute path from this shell.

## Player requests (in-game chats)
- Requests are often speech-to-text: guess the intended word first ("verity" may be a misheard name).
- **Unknown name (a mob, item, character, song, meme): web search it yourself right away, pick the most likely meaning, and build or do it.** Don't ask "what did you mean?" or offer options; ask only if the search finds nothing usable. Say in one line what you found and what you made.
- Same for anything needing outside info or assets (textures, sounds, references): fetch it yourself. Textures are still drawn by you.
- **Quality bar (player's standing order, all mods, even if it takes much longer):** a GOOD crazy mod, not a simple one: several spectacular abilities (the COOLEST idea, never the easiest to code, e.g. Space Stone = a real black hole sucking in mobs/blocks), a TON of new custom VFX (but few particles: shaped VFX layers, not particle spam), real mechanics (time stop = `/tick freeze`; reverse time = record ~5 s of the world and replay it backwards; meteors = real falling burning projectiles with trails, craters, debris), effects aligned with the real ray/hit, every ability its own UNIQUE VFX (never one shared primitive: not lines, not swirly circles), no lingering leftover effects, ultimates HUGE with a unique mechanic and fitting colors (all stones = rainbow), re-test ALL controls after every change, textures on everything (meteors too), time-stop effects keep animating while the world is frozen, reverse time rewinds all visible entities smoothly, disliked abilities get replaced by cooler ones. Test every ability in game. Full text: `tools/toolbox.md` (injected on every prompt).
- **Build the real thing, never a texture-only placeholder.** An item/block from a game, movie or idea must DO what it does there: abilities on right-click / sneak+right-click / hit / while held (a Java feature in `content/<Name>.java` with `@OnReload` hook + `@OnUnload`). Held items and objects get a **3D cube model** (`mc item <id> --cubes ... --tex ...`), not a flat sprite. Tell the player the controls in one line.

## Live removal
- One command for anything: `mc remove <id|"display name"|JavaFeature>` (`mc list` shows content + Java features). Java features = `content/<Name>*.java` (not the core systems): files deleted, one-line `Name.x();` calls/imports elsewhere removed, rebuilt.
- **Every Java feature that registers something (listeners, commands, ticks) must have a `@OnUnload` static method** that switches it off (guard flag false, remove command node), and its `@OnReload` hook must switch it back on (`enabled = true;` first). The G screen Mods On/Off runs exactly these two (`client/Projects.java`). Deleted classes stay loaded until restart; HotReloader runs `@OnUnload` when the .class disappears.
- Builds are serialized by `tools/lock.mjs` (`run/moddeus/build.lock`): parallel `game eval`s from several chats used to compile/delete each other's files.
- **Parallel chats/mods** (several mods built at once): every content-writing `mc` command holds `run/moddeus/content.lock` (shared en_us.json/sounds.json/tags lost keys when two wrote at once; nested mc calls inherit it via env). A compile error in one chat's file no longer blocks the others: `client/game/BuildSplit` holds the broken files plus files linked to them (old classes stay, retried next save) and builds the rest. `mc undo` in a mod chat undoes only that mod (bridge env `MODDEUS_PROJECT`; `--any` = anyone's newest change). Rules for chats: toolbox SHARED "PARALLEL CHATS". A mod running as generations ignores stray core loads of its original classes (`Gens.reload`), else its changes fell back to redefinition and waited for a restart.
`mc remove <id>` scrubs live (`ContentLoader.purgeRemoved`: inventories, ender chests, containers, placed blocks in loaded chunks, dropped items, stats) but **never unregisters items/blocks/sounds/entity types live** (`LiveRegistry.unregister` refuses): a missed copy crashed chunk saving ("Unregistered holder ... Block{[unregistered]}") and unregistering renumbers block-state ids. They stay registered but unused until the next launch.

## Physics bodies
`content/PhysicsBlock` = rigid body of real blocks (Sable/Create Aeronautics style): grid in the SPEC string, mass/COM/inertia from block materials, impulse solver vs world + other bodies, per-block buoyancy, sleeping. Entity pos = centre of mass. Not punchable/pushable: `client/content/PhysicsMining` mines cells (real break time, crack overlay) → `Physics.mine` → `breakCell` (drops, splits disconnected parts). Right-click with a block = `placeCell`. Players collide per cell (`Collisions`) and ride bodies they stand on. Renderer has no shadow.
- Contacts go BOTH ways (`gather`: own sample points in world/bodies + world block corners/edges and other bodies' points inside this one); a resting body under another is ground for it (shock propagation). After any solver change run `tools/tests/physics.java` (header says how; all lines PASS).

## Mixins
- `src/main/java/dev/moddeus/mixin` + `moddeus.mixins.json`. Mixins only apply at class load, so adding/changing one needs a restart; HotReloader skips that package. Keep mixins one-line delegations to a normal class (e.g. `LevelCollisionMixin` → `content/Collisions`) so the logic stays hot-swappable.
- A mixin class does nothing until it is listed in `src/main/resources/moddeus.mixins.json` (the dev config; `src/runtime/moddeus.mixins.json` is only the exported jar's). HumanoidPoseMixin/FirstPersonArmMixin were in the runtime list only, so no mod's body poses (BendPoses) ever played in dev and capes/VFX placed for posed bodies looked misplaced.
- World switch: a mod's statics belong to one world. `Gens.worldClosing` (SERVER_STOPPING) switches every running mod off, `Gens.worldOpened` (SERVER_STARTED) loads a FRESH generation (no static copy). A power once ticked a test dummy of the previous world: getChunk on a dead server thread froze the new world and "Save and Quit".
- **Stop the game BEFORE writing code that needs a restart** (new `defineId`, mixins): other chats run builds, and a half-applied swap crashed the game once (PhysicsBlock.OPTIONS null while saving).
- The dev run uses a fixed offline name (`--username Player224` in build.gradle): a random name each launch meant a fresh player.

## Lag (never again)
- **Mod Java code = generations, no JVM pause** (`client/Gens.java`): classes of a mod project (`content/<Id>*`, `client/content/<Id>*`) are never redefined. Each change defines a new generation (`Foo__g3`, same package, ~3 ms off-thread) and switches over on the server thread (~5-10 ms, async): ANY change (fields, methods, records, new classes) is instant. `Event.register` inside mod code is rewritten to stable slot proxies (no doubled listeners), static fields carry over by name, the mod's guard System properties are cleared, then its `@OnReload` runs. Mods load at startup via `Gens.startAll()`: do NOT call mod hooks from `Moddeus.onInitialize` (core referencing a mod class makes it fall back to redefinition). Also falls back for a mod class that extends a Minecraft class (Item/Entity/Screen...: objects that live in the world): keep those in core or data-driven (`mc item/mob`). `game run` snippets are remapped to the live generation. Log: "Hotswap (generation)".
- **Core code** (everything else) uses STANDARD redefinition only (`HotReloader.redefineFast`, method bodies, ~60-80 ms global safepoint). **No DCEVM** (`-XX:+AllowEnhancedClassRedefinition` removed): its replaced classes crashed the JVM 3x in G1 remark. A core change that adds/removes/changes fields, methods, constructors or lambdas is **deferred to the next restart** (`SwapCheck.schemaChanged`, log "Hotswap deferred"); body-only classes that call a waiting class's new members wait too ("waits (uses ...)"); everything else still swaps. So put new core logic in NEW classes (they load live) and keep edits to existing core classes body-only.
- **Sounds**: `client/SoundFast` (hooked in LightReload) parses sounds.json off-thread and swaps it into the live SoundManager (~1 ms, worst frame ~14 ms); never the SoundEngine.reload (OpenAL restart + atlas re-stitch, ~280 ms hitch). Guide: mc-content SOUNDS.md.
- **Datapacks** (`live/DataReload.java`): `game cmd reload` swaps only changed .mcfunction files (~2 ms, file scan off-thread, then #load like vanilla); other data changes = vanilla /reload (~300 ms). **Resource packs** `run/resourcepacks/*-RP` are watched: edits light-reload (~20-100 ms) by themselves.
- **Lag guard** (`client/LagGuard.java`): times every server tick, runs/times each datapack tick function itself (takes over `ServerFunctionManager.ticking`), mixin `ServerFunctionManagerMixin` times other function calls, watchdog samples slow ticks/frames (Java frames per mod). Sustained lag (>60 ms/tick or <25 FPS for 5 s, ignoring 15 s after reloads/toggles/swaps and vanilla FPS throttling: AFK/minimized = `FramerateLimitTracker` 10 FPS cap, not lag) NEVER switches anything off: it sends the mod's chat (bridge `forward`, `quiet` = no focus jump) what lagged, the numbers and how to fix it, once per 3 min, + one chat line. `run/moddeus/lag.json`, live: `node tools/mc.mjs game lag`. A runaway datapack function (65536-command limit every tick) froze the game once.

## Hotswap gotchas
- **Never Safe Mode**: one broken datapack file or a reference to an entry that only existed live fails the WHOLE world load. `tools/preflight.mjs` runs in play.bat before every launch and in `mc test refs`: drops unknown tag entries, quarantines bad JSON and loot tables/recipes naming missing items (`run/moddeus/quarantine/`), makes jukebox songs use an inline sound, deletes stale `build/resources` copies of files deleted from src. `client/LoadRescue` catches the Safe Mode screen in game, quarantines the files named in the registry errors, runs preflight and reopens the world. Dynamic-registry content (banner patterns, songs, trims, enchantments...) must ALSO be written as `data/<ns>/<registry>/<id>.json`.
- **Fabric "Missing content detected" screen** (quick play stops on it: no world, no game API, OS-sent keys/clicks don't reach the window): `<world>/data/fabric/registry_entries.dat` still names a deleted mod's namespace. preflight now moves such a snapshot to quarantine (Fabric writes a fresh one). Also: never launch play.bat twice; a second client can't lock the world ("locked a portion of the file").
- **Never loop in a `game run` / `Stage.after` snippet waiting for state that ticks advance** (`while (!crack(f, e)) {...}`): it runs ON the server thread, so ticks never come and the world freezes (player saw "server frozen"; Chronarch test, needed a JVMTI agent to break). Use `every(...)`/`after(ticks, ...)` and check once per tick, with a cap.
- Hitch diagnosis: `SwapHitch` samples the render thread for 3 s after every swap and logs the worst frame with its cause ("Hitch: ... | cause: ..."; slow ones also in `run/moddeus/hitches.log`). Texture redraws of existing sprites skip the reload (`client/Pixels`, ~1 ms). Never do slow work (PNG encode, process start, file IO) on the render thread.
- JVM crashes in "VM Thread" during G1PauseRemark (hs_err, jvm.dll+0x81ec5a, 3x, always after DCEVM enhanced redefinitions): fixed by never using DCEVM (see Core code above). Do NOT use `-XX:-ClassUnloading`: since JDK 20 JIT code is freed only when classes unload, so the code cache filled, the JIT switched off and the game ran at 4 FPS. The dev run uses `-XX:ReservedCodeCacheSize=512m`.
- **Every class swap runs on the HotReloader thread** (GameApi `build` queues into `HotReloader.build`). A second thread redefining at the same time, or redefining classes the calling thread is running, crashed the JVM once (EXCEPTION_ACCESS_VIOLATION in "VM Thread", hs_err in run/).
- SourceBuild may only delete outputs of sources it just compiled: a branch that put ALL sources into the delete pass wiped build/classes and crashed the game (Bridge/OnUnload ClassNotFound). Class files are written via tmp + atomic move.
- `@OnReload` hooks of CORE classes run only on swaps, NOT at launch: call them from `Moddeus.onInitialize`. Mod project classes (`<Id>*`) are started by `Gens.startAll()` instead; never call them from core.
- Re-creating a deleted class (same name) REDEFINES the still-loaded old one: all its new statics start null (crashed Vfx.DEFS). Keep maps non-final and re-create them in the @OnReload hook.
- `System.getProperty(k)` returns null for non-String values: guards stored with `put(k, Boolean.TRUE)` must be read with `System.getProperties().get(k)` (an "add new events" guard silently never fired).
- Event callbacks can't be unregistered: register once per JVM (guard with a System property) and only with method refs (`Foo::bar`), never lambdas, so swaps reach the new code.
- Changing a brigadier command's argument names: remove the old literal node from the dispatcher root first (reflection on `children`/`literals`), else the old node wins.
- `gradlew processResources` skips files whose content didn't change (touch doesn't help); to re-run ContentLoader use `mc game eval "dev.moddeus.live.ContentLoader.loadAll();"`.
- **Texture swap** (blocks showing other blocks' textures after an asset change): adding/removing a texture re-stitches the atlas, and chunk meshes built before keep the old UVs. `LightReload.done` calls `mc.levelExtractor.allChanged()` (what F3+T does) to rebuild them; never drop that.
- Lag: each swap = stop-the-world redefine (~300ms/20 classes) + JIT deopt. HotReloader waits for 1.5s of quiet so one build = one swap; assets use LightReload (no shaders/fonts/sounds, no loading screen).
- A NEW class is "new" only on its first load: after that it is a core class like any other, so a later field/method change to it is deferred too, `HotReloader.pendingRestart` releases a class again once its source is back to the live shape (remove the new field/method/lambda and save). Get the class shape right before saving, then iterate body-only, or put more logic in another new class. A lambda or method ref counts as a new method.
- A **static field added by a swap starts null/0**, because static initializers don't re-run. This includes `static final X = new ...`. It crashed the game once (Bridge.states). Use lazy init (`if (x == null) x = ...`) or set it in an `@OnReload` hook.
- **Instance fields added by a swap are null/0 on objects that already exist** (field initializers only run in constructors). Crashed the world once (PhysicsBlock.rotO). Null-guard them at the top of tick(), and wrap entity ticks in try/catch so a bug logs instead of crashing.
- New SynchedEntityData accessors (`defineId`) or a changed `createInterpolationHandler` only work after a game restart.
- **Anonymous classes are numbered by position** (`Foo$1`, `Foo$2`...): adding one ABOVE existing ones renumbers them and the swap fails ("attempted to change superclass or interfaces"), so nothing in that batch swaps. In core code use named nested classes, or add new anonymous classes below the old ones.
- **Never rename or remove a method that is registered as an event callback** (`UseItemCallback.EVENT.register(Foo::use)`): the registered ref still points at the old name and the next event crashes the game (NoSuchMethodError StormStaff.use, crashed once). Keep the old method as a one-line delegate to the new one. Same when deleting and re-creating a class.
- **Indexes saved before a swap can be out of range after it** (a list that shrank): clamp with `Math.floorMod(i, arr.length)` when reading stored selections. An unclamped one crashed the server tick (StormStaff.sel).
- Already-running loops keep their old frame, and only the methods they call pick up new code.
- **Test helpers that `game run` calls must be time-boxed (~80 ms per call, resume on the next call)**: `SuperpowersOriginClient.dryRun()` drew ~4500 overlay frames in ONE call on the server thread (~12 s); 8 parallel test agents calling it froze the world 10 s at a time, over and over (player: "keeps freezing"). Find such stalls: "Can't keep up" in latest.log + the agents' transcripts for `game run` in that window; `Gens: slow @OnReload / slow carry-over` lines name slow swap work.
- **Never an unbounded loop in a `game run` snippet / `s.after`** (`while (!f.broken) crack(f)` spun forever when crack refused: server thread froze ~4 min). Always cap (`for (i < 5 && ...)`). Rescue without restart: a jcmd `JVMTI.agent_load` agent that sets the exit field by reflection AND `retransformClasses` the inlined class (C2 hoisted the field read; the retransform deopts the loop). Agent class name must be new per load.
- If the in-game reloader itself breaks, use the out-of-band rescue: `gradlew rescueJar classes clientClasses`, then `.tools/jbr/bin/jcmd <pid> JVMTI.agent_load <abs>/build/agent/moddeus-rescue.jar <abs project dir>` (pid from `.tools/jbr/bin/jps -l`, the `devlaunchinjector` entry).

## Finding Minecraft APIs
- **Client END_CLIENT_TICK runs after vanilla's jump**: on the tick the jump key is pressed the player is already off the ground, so an "airborne + key pressed" check fires on the ground jump itself (double jump merged into one). Require a few airborne ticks (`client/AirTime`).
- **26.3 datapack formats**: `block_display` `block_state` is a string (`block_state:"minecraft:stone"`, like falling_block `BlockState`), the {Name:..} compound silently renders nothing; predicate player checks = `"predicate":{"minecraft:type_specific/player":{"advancements":{..}}}` (sub-predicate ids: `minecraft:entity_type`, `minecraft:flags`...); advancement `entity` condition = one `{"type":"minecraft:entity_properties",...}` object; `time query daytime` is gone, use `time query minecraft:day` (timelines). A bad predicate/advancement fails the WHOLE /reload (old data stays).
- **26.3 hit cooldown** = `LivingEntity.damageCooldownTime` (public), NOT `invulnerableTime`: resetting only invulnerableTime dropped every second power hit within 10 ticks.
- **26.3 inline item modifiers** use `type:` not `function:` (`item modify entity @s weapon.mainhand {type:"minecraft:set_custom_model_data",flags:{values:[1b],mode:"replace_all"}}`).
- **Key codes in 26.3 are SDL scancodes** (`KeyEvent.key()`: Enter = 40, Esc = 41), not GLFW (257/256). Always compare with `InputConstants.KEY_*`, never raw numbers or `GLFW.GLFW_KEY_*` (the Talk screen's Enter silently did nothing).
- First-person hands/held items in 26.3 = `client.renderer.FirstPersonHandsAndItemsRenderer` (+ `client.player.FirstPersonHandsAndItems`, state `renderer.state.level.FirstPersonHandsAndItemsRenderState`); there is NO `ItemInHandRenderer`. Third-person = `entity.layers.ItemInHandLayer`.
- Common 26.3 moves: entity type constants are in `EntityTypes` (`EntityTypes.PIG`), not `EntityType`; mobs live in sub-packages (`animal.pig.Pig`, `monster.zombie.Zombie`, `monster.illager.Pillager`, `npc.villager.Villager`); Enderman is `monster.Enderman`.
- 26.3 names differ from older tutorials. Verify before use: `.tools/jbr/bin/javap -cp <jar> <class>`, with jars in `.gradle/loom-cache/minecraftMaven/net/minecraft/` (common + clientOnly).
- 26.3 entity type constants live in `net.minecraft.world.entity.EntityTypes` (not `EntityType`): `EntityTypes.PIG`, `.CHICKEN`, `.ENDERMAN`, `.IRON_GOLEM`, `.LIGHTNING_BOLT`. Classes moved into subpackages: `animal.pig.Pig`, `animal.chicken.Chicken`, `monster.Enderman`, `animal.golem.IronGolem`. Matching by id avoids class names: `BuiltInRegistries.ENTITY_TYPE.getKey(e.getType()).getPath().equals("enderman")`. Entity tags: `entityTags()`.
- 26.3 renames: velocity sync flag = `Entity.needsSync` (no hurtMarked); `LivingEntity.swing(hand, SwingAnimation.DEFAULT, true)`; `entity.entityTags()`; client open screen = `mc.gui.screen()`; attack swing progress = `LivingEntity.getSwingAnimation(pt)` (no getAttackAnim); walk cycle = `walkAnimation.position(pt)/speed(pt)`.
- Cutscenes: `client/Cutscene.java` builder, guide `.claude/skills/mc-content/CUTSCENES.md`; from server code `Quick.cutscene("Name")`.
- Shaders: `.claude/skills/mc-content/SHADERS.md`. A custom `RenderPipeline` without `.withColorTargetState(...)` crashed the game on first draw ("color attachment count must match"). Shader/post_effect edits hot-reload (LightReload re-runs ShaderManager).
- VFX run on a real-time clock (`VfxClient.now`), so they keep animating during `/tick freeze`.
- **Blending in 26.3**: `RenderTypes.eyes()` is TRANSLUCENT (alpha blend), NOT additive (core VfxClient "glow" uses it). Additive = `RenderTypes.energySwirl(tex, 0, 0)` (ONE,ONE: alpha ignored, so the texture must be premultiplied, black = invisible). Soft glows with `eyes` showed as squares and dark rings.
- **Vanilla `energySwirl` writes depth and sorts AFTER translucent** (sortKey 47 vs entityTranslucent 29): additive glows hid the first-person arm/held item and painted over fire sheets. Superpowers uses its own copy (`SuperpowersClient.additive`: same snippet/blend, `writeDepth=false`, sortKey set by reflection to translucent-1 so textured layers draw over glows); player confirmed fixed. First-person arm = its own pass after the world: quads near the camera go into `GameRenderer.handAndScreenSubmitNodeStorage` (`SuperpowersClient.handLayer`). That pass projects with `hudFov` (not the game FOV), so moved quads are re-placed by `handFix` (v' = V^-1 Phud^-1 Pworld V v, from `gameRenderState.levelRenderState.cameraRenderState`) and only quads at the hands (`HAND_ZONE`) move: without it world VFX you walked up to split apart, jumped up and grew.
- Gens carries statics over through `client/GenMigrator`: old-generation objects, also INSIDE JDK containers (List/Set/Map/Object[]), are rebuilt as the new generation's classes (fields by name, shared refs stay shared). Brickjaw JOBS (`List<Object>` of `Object[]`) holding `BrickFight__g32` crashed the server tick with ClassCastException after a swap; dropping such fields instead orphaned live villain fights/boss bars and wiped `Superpowers.FX`. A field that can't be rebuilt (immutable container, removed enum constant) starts fresh (log "Gens: X.f starts fresh"). Check: `tools/tests/gens-migrate.java` (header says how). Keep GenMigrator top-level: a class nested in Gens changes its NestMembers and defers every Gens change to a restart.
- VFX render order: `VfxClient.late` submits into the after-terrain phase (like particles), and `CloudOrderMixin` → `client/RenderOrder` runs that phase after clouds. Custom glow geometry submitted the normal way gets painted over by water and clouds behind it (they write no depth). `RenderOrder.afterClouds=false` restores vanilla order.
- Project skills in `.claude/skills/` (minecraft-modding, resource-pack, datapack, commands, worldgen, testing, imagegen).
